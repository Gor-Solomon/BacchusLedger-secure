# ADR 0002: EF Core for persistence

Status: accepted (branch `refactor/ef-core`)

## Context

After the layering refactor (ADR 0001), all SQL lived in 14 `Sqlite*Repository` classes on top of home-made helpers
(`SqliteSession`, `SqliteRow`, `RecordFilter`, a connection factory with an `AsyncLocal` transaction). The schema was a
`CREATE TABLE IF NOT EXISTS` string plus a hand-written list of `ALTER TABLE` migrations, and several services created
tables on the fly (`EnsureTablesAsync`). Every query mapped rows by column name by hand.

## Decision

Use EF Core 8 (`Microsoft.EntityFrameworkCore.Sqlite`) in the Infrastructure project only.

- **Model**: one persistence entity per table (`Infrastructure/Persistence/Entities`) and one `IEntityTypeConfiguration<T>` per entity
  (`Configurations/`) that maps to the existing snake_case table and column names, types, keys, unique indexes, foreign keys and CHECKs.
  Domain and Application have no EF Core reference; repositories map entities to the same records as before.
- **Migrations**: `InitialSchema` creates exactly the old schema (checked column by column against a database made by the old code).
  It was edited by hand after generation: no `AUTOINCREMENT` (the old tables reuse ids after a demo reset), no declared `rowid` column on
  the four tables without a key, and key columns without `NOT NULL`, as in the old `CREATE TABLE` statements.
  `DatabaseInitializer` runs `Database.MigrateAsync()` at start. A database made before EF Core (tables, but no `__EFMigrationsHistory`)
  is *baselined*: `InitialSchema` is recorded as applied and all data is kept. `RESET_ON_START` / "Reset demo data" migrate down to nothing
  and up again, then seed.
- **Repositories**: LINQ with `AsNoTracking` for reads; inserts save at once (the new id is needed right away); updates and deletes use
  `ExecuteUpdate` / `ExecuteDelete`. Loops over batches load their data with one query per kind of data (`AnalyzeManyAsync`), not one per batch.
- **Unit of work**: `IUnitOfWork` uses the DbContext transaction (`BeginTransactionAsync`, `SaveChangesAsync`, commit / rollback for the
  selftest probes). Writes are still serialised by one lock, as before. The DbContext is scoped; the background live simulator opens a DI
  scope for every step.
- **SQLite settings** are the same as before: foreign keys on, wait up to 5 s for a lock (connection string `Default Timeout=5`, was
  `PRAGMA busy_timeout=5000`), default journal mode (WAL was never used).

## Where raw SQL is still used, and why

| Place | Why |
|---|---|
| `Migrations/…_InitialSchema.cs`: the 4 append-only triggers on `operations` and `readings` (`migrationBuilder.Sql`) | EF Core has no model for triggers. |
| `EfDiagnosticsRepository.SnapshotAsync`: `sqlite_master`, `COUNT(*)` / `MAX(rowid)` per table | The selftest's "nothing was written" check covers every table, also ones the model does not know; `rowid` has no model. Table names come from `sqlite_master` and are checked (letters and `_` only) before they go into the SQL text. |
| `EfDiagnosticsRepository.TryChangeAppendOnlyAsync`: 4 fixed UPDATE/DELETE statements | It must hit the real database triggers. Only these four statements can run. |
| `DatabaseInitializer.BaselineLegacyDatabaseAsync`: EF Core's own history-table scripts (`IHistoryRepository.GetCreateIfNotExistsScript` / `GetInsertScript`) | Generated by EF Core, not hand-written; needed to mark an old database as already migrated. |

All other database access is LINQ.

## Consequences

- No hand-written SQL strings or row mapping; schema changes are migrations (`dotnet ef migrations add <Name> -p src/BacchusLedger.Infrastructure`).
- The seal still hashes rows column by column: rows read through EF Core give the same values and types as the old reader (test:
  `SealCompatibilityTests`), and databases sealed by the old code still verify.
- Application services are scoped (they use scoped repositories).
